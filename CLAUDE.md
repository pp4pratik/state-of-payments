# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`state-of-payments` (branded **UPI Pulse**) is a single-page dashboard tracking India's UPI/AutoPay ecosystem and RBI payment-systems data (views: UPI / UPI AutoPay / RBI Cards / RBI Payments / Circulars). It reads entirely from static JSON checked into `public/`, generated by Python scripts that scrape NPCI/RBI directly. There is no backend, no database, no API server.

## Commands

```bash
npm install
npm run dev      # vite dev server
npm run build    # vite build && tsc -b --noEmit  (type errors fail the build)
npm run lint      # oxlint
npm run preview   # preview the production build
```

No `.env` is needed to run the app — everything it reads is static JSON already committed under `public/`.

There is no test suite. Correctness is verified by `npm run build` (type-check) plus manually exercising the app in a browser (all 5 views, both Volume/Value toggle states, a spread of months/years) and checking `read_console_messages` for errors — that's the standard verification loop for any frontend change here.

To refresh the data (see **Data pipeline** below):

```bash
python3 scripts/fetch_rbi_data.py                              # RBI Cards + RBI Payments
python3 scripts/fetch_rbi_data.py --dry-run

pip install playwright && playwright install chromium          # one-time setup
python3 scripts/fetch_npci_data.py                              # everything else
python3 scripts/fetch_npci_data.py --dry-run
python3 scripts/fetch_npci_data.py --only=circulars,app_stats   # just specific domains
```

Neither script needs a `.env` — both scrape their source directly and write straight to `public/data/`.

## Architecture

### Data store: static JSON, not a database

- `public/data/<table>.json` — one file per table (`monthly_trend`, `app_stats`, `p2p_p2m`, `merchant_categories`, `circulars`, `autopay_registrations`, `autopay_executions`, `autopay_registrations_by_bank`, `autopay_executions_by_psp`, `psp_member_performance`, `rbi_cards`, `rbi_payments`). Each is a flat array of plain objects keyed by snake_case column names. Multi-row-per-month tables hold every month's rows in one array; the 5 "latest month" tables (`autopay_*`, `psp_member_performance`) hold only the single most-recently-fetched month.
- `public/statewise-historical/` — Geography is the one exception to "one file per table." A month's payload can run to ~780 districts, too big to lump into one array like everything else, so it's one JSON file **per month** plus an `index.json` manifest listing which months exist. `src/lib/queries.ts`'s `useStatewiseAll` fetches the manifest, then fetches every listed month in parallel.
- There used to be a Supabase Postgres backend and an Airtable audit trail; both have been fully retired (see `supabase/schema.sql`'s header and `supabase/migration_004_drop_statewise.sql` / `migration_005_drop_remaining_tables.sql` for how the tables were dropped). Don't reintroduce either without being asked — this migration was deliberate.

### Data pipeline: Python scripts write straight to JSON

- `scripts/fetch_npci_data.py` — scrapes npci.org.in for everything except RBI's own two tables and P2P/P2M. NPCI's stats API is behind Akamai bot protection that blocks plain HTTP (`curl` gets a 403), so this uses Playwright (headless Chromium) instead of `urllib`. **P2P/P2M Transactions has no automated source** — NPCI's own site 500s on that tab for every month tested; hand-edit `public/data/p2p_p2m.json` directly when new figures are available.
- `scripts/fetch_rbi_data.py` — scrapes rbi.org.in for RBI Cards and RBI Payments. No bot protection there, plain HTTP + HTML table parsing works.
- `scripts/json_store.py` — shared write helpers both scripts use, replicating the semantics the old Supabase pipeline relied on:
  - `upsert_single(name, unique_cols, row)` — one row per natural key (the single-row-per-month tables).
  - `replace_for_key(name, key_col, key_val, new_rows)` — delete every row matching one column's value (typically a month), then insert the fresh batch. This is what makes a renamed or dropped entity not leave a stale row behind — a pure upsert can't do that.
  - `upsert_many(name, unique_cols, new_rows)` — merge by unique key, no scoping (used for circulars, which aren't month-scoped).
  - `distinct_values(name, column, exclude_key_col, exclude_key_val)` — reads back existing values of a column, used for entity-name normalization below. **Always exclude the month currently being written** from this query, or a bad spelling written in a previous run becomes its own "established" reference and self-perpetuates.
- **Entity-name spelling drift**: NPCI's own entity-name spelling isn't stable month to month (e.g. "PhonePe" → "Phone Pe" for one month). `normalize_key`/`normalize_names` in `fetch_npci_data.py` snap an incoming name back to an already-established spelling (case/whitespace-insensitive match against every other month already in the JSON file) before it gets keyed by anything — otherwise a spelling hiccup silently forks a time series into two. This applies to `app_stats`, `psp_member_performance`, and all four AutoPay breakdown tables (see `NAME_FIELDS` in `fetch_npci_data.py`); not to Merchant Categories (MCC is a stable numeric code) or Geography (state/district names don't drift).
- Multi-row-per-month domains use delete-then-recreate (`replace_for_key`) rather than trying to match individual entities row-by-row across runs — simpler and safer.

### Frontend

- Vite + React 19 + TypeScript. Single route (`src/routes/index.tsx`, TanStack Router) — view-switching between UPI/AutoPay/RBI Cards/RBI Payments/Circulars is client state (`src/lib/DashboardContext.tsx`'s `ViewKey`), not real routing.
- `Landing` (in `routes/index.tsx`) is a 3-screen switcher: `landing` → `explainer` (an educational walkthrough, `ExplainerView`) → `dashboard`. Only `dashboard` mounts `DashboardProvider` and the data-fetching views.
- `DashboardProvider` holds the shared `view` / `metric` (Volume vs Value) / `selectedMonth` state that every view component reads via `useDashboard()`. `months` (the selectable Jan'25–Jun'26-ish range) comes from `useAppStatsAll()`'s result, fetched once in `Dashboard` and passed down — every other view component assumes this month list is authoritative.
- Data fetching lives entirely in `src/lib/queries.ts` — one `useXxx()` TanStack Query hook per JSON file, each just `fetch()`-ing a static file (no pagination, no auth, no loading-state coordination beyond what TanStack Query gives for free). When adding a new data domain, add a hook here first, matching the existing pattern (plain `fetch` + `res.json()`, sorted/grouped client-side as needed).
- **Cross-dataset month lookups must match by month string, not array position.** Different tables cover different date ranges (e.g. `p2p_p2m` only starts Jan 2025 while `app_stats` goes back to 2024) — indexing one array by another's position silently misaligns or breaks. Always resolve a target month explicitly (`array.find(r => r.month === month)`) rather than assuming two datasets' arrays line up index-for-index.
- Charts: Chart.js via `react-chartjs-2`. Numbers are normalized to a single **Crore** unit throughout (`src/lib/format.ts`, `mnToCr`/`rbiCountToCr`) so figures read consistently across every view regardless of the source unit (millions, raw counts, etc).
- Theming: `src/lib/useTheme.ts` is parameterized by `storageKey`/`defaultTheme` — the landing/explainer screens default to light and persist under one localStorage key, the dashboard defaults to dark and persists under another, independently.
- `src/components/IndiaMap.tsx` renders Geography's choropleth from a vendored, simplified topology (`public/india-states.topo.json` — predates 2019's J&K/Ladakh split and 2020's Dadra & Nagar Haveli/Daman & Diu merger, so it has its own name-mapping table to NPCI's current state names).
- Analytics: PostHog (`posthog-js`), gated behind `VITE_POSTHOG_KEY` — a no-op if unset.

### Deployment

Push to `main` → GitHub Actions (`.github/workflows/deploy.yml`) runs `npm run build` and publishes `dist/` to GitHub Pages. The JSON data ships as part of the static build (`public/` → `dist/`), so there is nothing else to deploy or provision. Site is served at the `/state-of-payments/` base path (`vite.config.ts`); update that if a custom domain is ever attached.
